<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser/curl -> POST /api/chat | untrusted free text that can move simulated money |
| chat response (mock now, LLM later) -> action executor | untrusted structured actions |
| request handlers -> SQLite / trade_lock | concurrent writers |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Tampering | chat/execute.py actions | mitigate | every trade re-validated with `TradeRequest` (Ticker regex, strict Quantity 0 < q <= 1e6, 4 dp) and `execute_trade` validation; watchlist tickers via `normalize_ticker`; tests for bad ticker, negative/too-precise qty, oversell, insufficient cash |
| T-04-02 | Denial of service | run_actions | mitigate | `MAX_ACTIONS = 10`, extras recorded as skipped; ChatRequest max_length 2000 -> 422 |
| T-04-03 | Tampering | concurrent chat + manual trades | mitigate | services own `trade_lock`, callers never hold it (no re-entrancy deadlock); same critical section as Phase 3 CR-02 |
| T-04-04 | Tampering | SQL in chat/store.py | mitigate | parameterized `?` placeholders only |
| T-04-05 | Information disclosure | 422 handler | mitigate | existing handler omits request input |
| T-04-06 | Tampering | prompt injection via user text driving trades | accept | single-user, fake money, auto-execute by design (PLAN.md section 9); validation and action cap still apply |
</threat_model>
